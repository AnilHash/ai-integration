## Qdrant Gotchas & Insights (Scale Benchmark)

### Indexing behavior

- **`indexing_threshold` is a per-segment KB size, not a global switch.** Small collections (even 10k-100k vectors) can sit below the default 20,000 KB threshold _per segment_ (since Qdrant auto-splits into multiple segments), so `indexed_vectors_count` never advances — looks like a hang, isn't one.
- **`indexing_threshold=0` disables indexing entirely** — it's a sentinel, not "always index." Counterintuitive; use `1` (or a small positive number) to force near-immediate indexing instead.
- **Two-phase indexing (disable during upload, enable via `update_collection` after) did NOT meaningfully change total time** in our tests — per-batch reindex thrashing wasn't actually the bottleneck at our scale. Don't assume this optimization helps without measuring.
- **Index build time dominates and scales superlinearly with n** — in our runs, indexing became ~4x the upload time by 500k vectors. This is inherent to HNSW (each insert searches the existing graph), not a bug. Report upload and index time as separate line items.
- **`models.OptimizersStatus` is a typing construct, not a real enum** — can't do `.OK` on it. Compare `info.optimizer_status` directly to the string `"ok"`.

### Uploads

- **`upload_points(..., batch_size=5000)` over REST can exceed Qdrant's default 32MB request body limit** — JSON-encodes floats as text (~15-20 bytes/float vs 4 bytes raw), so a batch that looks small in raw bytes can balloon 2-3x over the wire. Either switch to `prefer_grpc=True` (binary protocol, no bloat) or shrink `batch_size` for REST.
- **`prefer_grpc=True` requires port 6334 exposed** in Docker (`-p 6334:6334` / compose `ports:`), separate from the REST port 6333. `Connection refused` on 6334 is unhelpful compared to just checking `docker ps` for the port mapping.
- **`parallel=N` in `upload_points` multiplies peak memory** — each worker process holds its own batch in memory. On memory-constrained hosts, prefer sequential `client.upsert()` in a loop, or keep `parallel` low.
- **Generate vectors in chunks, not all upfront.** `rng.normal(size=(500_000, 768))` alone is ~1.5GB before Qdrant even sees it, and this runs on the _host_ process (unconstrained by any container `mem_limit`). Stream generation + upload per-batch to bound peak memory to batch size, not n.

### Windows / WSL2 / Docker Desktop specifics

- **WSL2 has no default memory ceiling and can balloon to ~80% of host RAM**, starving Windows itself — symptom: screen goes dark, mouse cursor still moves (display driver starved). Set explicit caps in `%UserProfile%\.wslconfig`:
  ```ini
  [wsl2]
  memory=6GB
  processors=4
  swap=4GB
  ```
  Requires `wsl --shutdown` + Docker Desktop restart to take effect.
- **`mem_limit` in docker-compose only caps the container, not the WSL2 VM itself.** Other processes (Docker overhead, your Python host process) can still push total WSL2 memory high enough to freeze the host.
- **More WSL2 cores isn't free — can cause CPU oversubscription** with the host OS, actually _worsening_ performance in our case (100k index time went from ~403s pre-change to ~1112s right after bumping to 4 cores). Possible causes: contention with host processes, thermal throttling on a laptop CPU under sustained load, or Qdrant not using the extra cores without explicit config.
- **`max_indexing_threads` must be set explicitly** — Qdrant doesn't automatically scale indexing thread count with newly available WSL2 cores. Setting it (we used `2`) alongside `processors=4` in `.wslconfig` recovered some of the lost performance (100k index dropped from ~1112s to ~779s).
- **WSL2's `.vhdx` virtual disk doesn't shrink automatically after deletes.** Repeated `delete_collection`/`create_collection` cycles across many benchmark iterations may leave a larger/more fragmented virtual disk than a fresh volume, inflating I/O time in later runs. Suspected but not fully confirmed — worth a `docker compose down -v` + fresh volume before final/reported numbers.

### Query latency / cold vs warm

- **First query against an `on_disk=True` collection pays a real cold-cache penalty** (~140ms cold vs ~25-30ms warm in our test) — OS page cache hasn't loaded graph/vector pages from disk yet. Expected behavior, not a bug.
- **`indexed_vectors_count >= n` can be true while background segment merging is still running** — check `optimizer_status == "ok"` too, or query latency benchmarks may be measuring mid-merge contention rather than steady state.

### Benchmark methodology takeaways

- Timer placement matters: a `while True` polling loop wrapped in the same timer as the upload call silently measures upload + index + wait combined, not just upload — mislabel risk if not split explicitly.
- Docker container logs (`Creating collection` / `Updating collection` timestamps) are a more reliable ground truth for phase timing than in-script instrumentation, since they're untouched by any Python-side bugs.
- `docker stats` (CPU/memory/disk/network graphs) is the fastest way to confirm whether a phase is actually running vs silently stalled — flat lines across all four = process is stuck, not Qdrant.
- For iterative debugging, test on the smallest representative scale (`10k`/`100k`) before committing to a full `500k` run — round-trip cost matters when each big-scale attempt costs 15-80+ minutes.
